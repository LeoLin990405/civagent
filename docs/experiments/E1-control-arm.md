# E1 control arm — real topology versus random wiring

Status: prepared, not run. This document contains no control-arm result.

## Question and unit of comparison

The original E1 compared five historical regimes but had no null topology. This
follow-up asks a narrower question: holding a regime's offices and persona
constant, does its declared wiring outperform a seeded random rewiring?

Each tournament contains five pre-registered source/control pairs:

| Source | Random-wiring control |
|---|---|
| `china/qin` | `_baseline/qin-random` |
| `china/tang` | `_baseline/tang-random` |
| `global/athens` | `_baseline/athens-random` |
| `china/zhou` | `_baseline/zhou-random` |
| `china/ming` | `_baseline/ming-random` |

All five controls were generated by `engine/baseline.mjs` with decimal seed
`42`. The source office ids, labels, duties and SOUL are retained; the declared
edges and the matching Decision Flow prose are rewired. The control therefore
tests this generator's wiring intervention, not an abstract claim that every
possible random graph is equivalent.

## Pre-registered predictions (written before the first control match)

Registered 2026-07-30, before `--execute` was run even once. The design above
was fixed by the orchestrator; these are the claims it will be judged against.

- **C1 (primary).** Across the 15 source/control pairs (5 pairs × 3 scenarios),
  the historical wiring beats its seeded random rewiring in a clear majority.
  *If random wiring wins or ties as often as it loses, then topology — as this
  generator varies it — does not measurably affect output quality, and the
  project's central proposition is unsupported by this experiment.* That
  outcome is to be reported as plainly as the favourable one.
- **C2.** Pairs whose gap is smaller than the judge's own pass-to-pass position
  effect are reported as **unresolved**, never as a win or a loss. C1 is scored
  only over resolved pairs, and the count of unresolved pairs is reported.
- **C3.** Every arm's transcript-selection metadata shows office-level coverage.
  A pair where either side fell back to a raw-log tail is excluded from C1 and
  reported separately — that arm was not measured, it was sampled by accident.

One prior datapoint, stated so it cannot be quietly forgotten: in the original
E1 smoke run `baseline/tang-random` scored **10** against `china/tang`'s 7.9.
That run predates the transcript-capture fix, so it is not evidence about
topology — but it is a reason not to assume C1 before seeing the numbers.

### Scope this cannot settle

The controls are generated by one seeded rewiring per regime (seed 42). A
result either way is about *this* intervention on *these five* regimes at
n = 1 per cell, not about random graphs in general.

## Fixed execution design

- Scenarios: the same three ids registered in E1:
  `plague-response-01`, `regional-militarization-01`,
  `border-city-autonomy-01`.
- Backend: `cn:doubao` for every arm.
- Each scenario/repeat is one ten-civ tournament, preserving all five paired
  contrasts inside the same judge context.
- Judging remains anonymized and order-swapped.
- `--no-skill` is applied to all ten civs so learned skills do not exist only
  on the historical side of a pair.
- Repeats are an explicit operator choice. This preparation does not select an
  `N` after seeing results.

The primary analysis should report each source-minus-control paired difference
by scenario and repeat. It must also retain the judge's position effect and
transcript-selection manifest. A pair whose gap is not distinguishable from
the judge's own pass-to-pass movement must be reported as unresolved, not as a
win or loss.

## Reproducible launcher

Dry run (the default; no model calls and no state writes):

```bash
node scripts/e1-control-experiment.mjs --repeats 1
```

Machine-readable plan:

```bash
node scripts/e1-control-experiment.mjs --repeats 1 --json
```

Execution is deliberately gated:

```bash
node scripts/e1-control-experiment.mjs \
  --repeats <N> \
  --execute \
  --estimated-afp-per-job <value-from-provider-telemetry> \
  --concurrency 1 \
  --batch-size 1 \
  --cooldown-ms <operator-chosen-delay>
```

The launcher uses a fixed-window limit of 10,000 estimated AFP per five hours
by default and persists completed job ids under
`~/.civagent/experiments/e1-control-state.json`. It resumes completed jobs and
reserves the estimate before each spawn.

Important limitation: CivAgent does not receive measured AFP usage from the
provider. `--estimated-afp-per-job` is supplied by the operator from provider
telemetry. The limiter is therefore a conservative scheduling aid, not proof
that actual usage stayed below 10,000 AFP. Concurrency, batch size, cooldown,
limit and window are configurable; actual compliance must be checked against
the provider dashboard.

No command with `--execute` was run while preparing this control arm.
